# Architecture

## End-to-end flow: a task turn

A task's lifecycle spans many turns (dev claims -> works -> submits -> QA claims -> reviews -> ... -> PM/CEO approves); each turn is one fresh Cloud Run Job execution of one agent slug. There is no resumed chat session across turns — continuity comes from the task's own DB state and the evidence bundle handed to the next claim, not from ADK session memory (`InMemorySessionService` is per-process and dies with the container). One turn, end to end:

1. **Dispatch decides to spawn.** The orchestrator's dispatcher resolves which agent should act next (e.g. a developer picking up a `pending` task, or a QA claiming an `awaiting_qa` one) and calls `AgentOrchestrator.spawn_agent`, which resolves the agent's route (`ModelProvider`) and routes to the registered provider for that type. On this deploy every delivery role resolves to `ADK_CLOUD_RUN`: `bootstrap.main` calls `services.llm.seed_adk_cloud_run_routing()` at startup whenever `gcp_project_id` is set, which upserts a GLOBAL routing assignment pinning every agent at `ADK_CLOUD_RUN` (`robofleet/services/llm.py`). The predecessor's Claude Code CLI docker spawn path was removed outright (`robofleet/runtime/orchestrator.py`'s `_spawn_container` raises if no provider is registered for the resolved type).
2. **`CloudRunJobsProvider.spawn`** (`robofleet/llm/providers/cloudrun_jobs.py`) builds the Job's env vars: the agent's identity (UUID, role, team) and a fresh HMAC token signed by `issue_agent_token`, the orchestrator's own public URL (so the agent's HTTP calls can reach back), the flow-verb timeouts, and the model-auth block — `GOOGLE_GENAI_USE_VERTEXAI=1` + `GOOGLE_CLOUD_PROJECT` + `GOOGLE_CLOUD_LOCATION` when `gcp_project_id` is set (the real GCP path: the Job authenticates to Vertex AI with its own runtime service account, no API key), falling back to a Secret-Manager-backed `GEMINI_API_KEY` only when there is no GCP project (local dev). It uploads the composed tool-manifest JSON (flow/do verb lists + system prompt) to `gs://<bucket>/manifests/<agent-id>.json` and passes that URI as `ROBOFLEET_TOOL_MANIFEST_PATH`; if the task carries a project it looks up and forwards the project's decrypted git PAT as `ROBOFLEET_GIT_TOKEN`. Every secret-shaped value (the agent token, the git PAT, the API-key fallback) is written to a per-agent, rotated Secret Manager secret and referenced by the Job as a `secretKeyRef` rather than carried as a plain env value (`_secret_env` / `_rotate_secret`: a fresh version is added and every older enabled version destroyed, so a leaked handle can't replay a stale token) — only a deploy with no `gcp_project_id` (local dev) keeps the plain value. It then attaches the Filestore NFS volume (mounted at `settings.workspaces_root`, `/data/workspaces`) and the Serverless VPC Access connector when a task needs a workspace, sets a 2Gi/1-CPU resource limit (the ADK + google-genai + google-cloud-storage import set OOMs a default 512MiB job before it reaches its own exception handler), creates or updates the per-agent Cloud Run Job, and starts an execution.
3. **The Job container runs `robofleet.agent.adk_entry`** (`docker/agent-adk.Dockerfile`'s entrypoint). It fetches the tool manifest (from the `gs://` URI or a local path), builds an ADK `LlmAgent` on `gemini-3.5-flash` with two tool sets: `build_gateway_tools()` (`robofleet/agent/gateway_shim.py`, one `FunctionTool` per manifest verb, HTTP-backed) and `build_git_tools()` (`robofleet/agent/git_tools.py`, file read/write/delete/move + `git_commit`/`git_status`/`git_push` against the Filestore-mounted worktree). It runs the `Runner` over one `InMemorySessionService` session, accumulating token usage from each event's `usage_metadata` (summed across every model call, not overwritten — a real Gemini 3.x turn bills thinking tokens as output, which the accumulator folds in).
4. **Every gateway tool call is a plain HTTP POST**, not MCP: `gateway_shim.call_verb`/`call_do` resolve the orchestrator's base URL (falling back to a hardcoded public Cloud Run URL, `ROBOFLEET_PUBLIC_API_URL`, when the injected `ROBOFLEET_ORCHESTRATOR_URL` is a docker-mesh/loopback address unreachable from a separate Cloud Run Job container) and POST to `{base}/api/v1/flow/{segment}/{verb}` (`segment` is the role string, except `product_owner`/`head_marketing` which share `board`) or `{base}/api/v1/do/{tool}`, carrying `X-Agent-ID`/`X-Agent-Role`/`X-Agent-Team`/`X-Agent-Token`. The orchestrator's role-gated router (`robofleet/api/routes/v1/`) verifies the HMAC token, then hands off to the `Choreographer` (`robofleet/services/gateway/choreographer/`), which composes the existing domain services (`TaskService`, `GitService`, `JournalService`, `WorkSessionService`, ...) into that intent verb's atomic sequence and returns a standardized Envelope: `{status, task_id, next, evidence, context_briefing}` on success, or `{error, message, remediate, missing}` on failure — the model is steered by `next`/`remediate`, never left to guess state.
5. **`git_tools`' `git_commit`/`git_push` run real `git` subprocesses** against the per-task worktree at `ROBOFLEET_WORKSPACE_DIR`, on the same Filestore NFS mount the orchestrator's own git operations use, so the two see one consistent tree; `git_push` authenticates with the `x-access-token:<ROBOFLEET_GIT_TOKEN>` extraheader.
6. **On exit** — normal completion, a classified rate-limit (429/`ResourceExhausted`, exit 75) or auth (401/`Unauthenticated`, exit 78) failure, or a tool-loop cutoff (one tool rejecting 12 calls in a row, exit 0 so Cloud Run does not retry the whole Job) — `adk_entry` POSTs the cumulative usage counts to `POST /api/v1/usage/report` (`robofleet/api/routes/v1/usage.py`), which persists them onto the agent's open `agent_spawn_sessions` row (idempotent: a missing agent or session returns `{"status": "ok", "matched": false}` rather than 500, so a transient re-POST on restart is harmless).
7. **The orchestrator's `_check_health` loop polls the provider** once per tick: for a Cloud-Run-Job-backed instance it calls `CloudRunJobsProvider.execution_outcome` (reads the Execution's `Completed` condition — `CONDITION_SUCCEEDED`/`CONDITION_FAILED`; `None` while still running) instead of `docker inspect`. A finished execution is handed to `_handle_stopped_container`, which reads the usage counts back (`_cloudrun_session_counts`, from the same `agent_spawn_sessions` row `usage/report` wrote), finalizes the spawn session with cost pricing, and — on a genuine crash — auto-restarts up to a cap before escalating a stranded-agent notification to the auditor/CEO.

## Data stores

- **Cloud SQL (Postgres 16 + pgvector)** is the primary store: tasks, agents, work sessions, `audit_log`, `task_review_findings`, `agent_spawn_sessions`, notifications, journals, and the pgvector embedding indexes the in-house RAG engine (`OptimalService`) queries for the memory bank / knowledge base. Reached through the Cloud SQL Python connector (`robofleet.infra.cloudsql.async_engine_for_cloudsql`, `asyncpg` driver) whenever `gcp_cloudsql_instance` is set; `robofleet/db/base.py`'s `get_engine` branches on that setting, so a plain-DSN engine (local dev) is otherwise unchanged.
- **Memorystore for Redis 7.x** backs the event bus (Redis Streams with consumer groups — task/notification fan-out), the per-provider rate-limit state tracker, and general caching. TLS is off on this deploy (`ROBOFLEET_GCP_MEMORYSTORE_TLS=false` in `orchestrator-service.yaml`, since the provisioned instance has `auth_enabled = false` and no TLS listener — `gcp_memorystore_tls`'s config default of `true` would TLS-handshake a plaintext port and hang).
- **Filestore NFS**, mounted at the fixed path `/data/workspaces` on *both* the orchestrator Cloud Run service and every spawned agent Job (`settings.workspaces_root` is pinned there whenever `gcp_filestore_share` is set — see `Settings._apply_filestore_workspaces_root`), is the single shared root for per-project clones and per-task worktrees. Without the Filestore IP/path env vars set, `CloudRunJobsProvider._build_task_template` refuses to spawn a Job that needs a workspace rather than letting Cloud Run silently fail the container exec with no diagnostic output.
- **GCS is not a workspace store** — a real gap between the pre-existing `.mmd` diagram and the code. Two uses are live on this deploy: ① the per-spawn ADK tool-manifest JSON, uploaded once per spawn to `gs://<bucket>/manifests/<agent-id>.json` and fetched by the entrypoint (`_upload_manifest` / `gateway_shim._load_manifest_from_gcs`); ② best-effort diagnostic writes from inside the agent container — a `diag/run-<agent>.txt` heartbeat, a `diag/crash-<agent>.txt` traceback, and a `diag/request-<agent>.json` dump of the failing model request on a Vertex `400 INVALID_ARGUMENT` — so a container that OOMs or crashes before it could reach Cloud Logging still leaves a readable trace (`robofleet/agent/adk_entry.py`'s `_gcs_put`/`_dump_crash`/`_diag`, all fire-and-forget, never masking the real exit). A third use, video render uploads (`robofleet/services/video_renderer_client.py`), exists in code but is inert here: the video engine flag is off in `.env.gcp.example`.
- **Secret Manager** holds the six bootstrap secrets seeded once by `infra/seed-secrets.sh` (fernet key, agent-auth HMAC secret, cloud-auth secret, Gemini API key, Cloud SQL password, a generated CEO login password), wired into the orchestrator's Cloud Run manifest via `secretKeyRef` so no password sits as a plain service env value. Per spawn, the orchestrator additionally mints and rotates one-off secrets for that agent's own signed identity token and (when the task has a project) its decrypted git PAT — see step 2 above.
- **Artifact Registry** holds one Docker repo with the three images `robofleet-orchestrator`, `robofleet-panel`, `robofleet-agent-adk`, each built by Cloud Build (`cloudbuild.yaml`) and tagged with both the build's short SHA and `:latest`.

## Panel / orchestrator split

The orchestrator (`docker/orchestrator.Dockerfile`) is a single Cloud Run **service** running FastAPI + the WebSocket API, the Choreographer/gateway routes, and every `AgentOrchestrator` background loop (the dispatcher, the health-check/reap loop, the respawn-tracker DB write-through, the Redis Streams event-bus listener) in one process. `orchestrator-service.yaml` pins `min-instances: 1` (the background loops need a live instance even with zero inbound requests, not just on-request compute) and 2 CPU / 2Gi memory (the default 512MiB/1CPU OOM-kills a process this heavy). Its image still installs the `docker-ce-cli` binary and every code path from the predecessor that shells out to it (`AgentOrchestrator._run_container_cmd`, used for the interactive Intake/Secretary chat spawn) is unchanged — but Cloud Run gives the container no Docker daemon to talk to, so that one path does not work here; the Cloud Run Jobs delivery spawn path (`CloudRunJobsProvider`) never touches `docker` at all and is unaffected.

The panel (`docker/panel.Dockerfile`) is a separate, stateless Cloud Run service — a Next.js 16 app built with `output: "standalone"` — carrying none of the orchestrator's secrets. Its own Next server proxies `/api/*`, `/ws/*`, and `/health` to the orchestrator through `next.config.ts`'s `rewrites()`, resolved at **build time** (so `ROBOFLEET_API_URL` must be known when the image is built — `cloudbuild.yaml` passes it as a `--build-arg`, and WebSocket upgrades only ever ride this build-time rewrite, never request-time middleware). `proxy.ts` (Next 16's rename of `middleware.ts`) then does two things at **request** time. First, when `ROBOFLEET_API_URL` is set in the panel's runtime environment — `infra/panel-service.yaml` sets it, so it always is on Cloud Run — it rewrites every `/api/*` and `/health` request to the orchestrator directly (`proxy.ts:62-68`), ahead of any auth logic. That request-time path is what actually serves the panel's API calls on Cloud Run, where the build-time value baked into the image can be stale or absent; the build-time rewrite is the compose/local path and the only route WebSocket upgrades take. Second, for everything else it probes `/api/auth/status` server-side to decide whether an unauthenticated request to the dashboard route group is redirected to `/login`. So it is both the request-time `/api` proxy and the login gate, not only the latter.

Both Cloud Run services and every agent Job attach the same Serverless VPC Access connector (`robofleet-connector`, `infra/lb.tf`) so they can reach Cloud SQL's private IP and Memorystore over the `robofleet-net` VPC; Filestore is reached through a separate Cloud Run NFS volume mount, a distinct mechanism from the VPC connector. There is no nginx on this deploy: the docker-compose deploy's single-entry-point nginx (`/api`, `/ws` -> orchestrator; everything else -> panel) has no GCP counterpart here — the panel's own rewrites do that job, and the two services are reached directly at their own `.run.app` URLs unless an operator sets `lb_domain` in `infra/lb.tf` to provision the optional global HTTPS load balancer (path-based routing: `/api/*`, `/ws/*` -> orchestrator backend, everything else -> panel backend).

## Provider registry vs. what actually dispatches

`ModelProvider` (`robofleet/models/base.py`) has eight values: `anthropic`, `ollama_cloud`, `openai`, `local`, `grok`, `gemini`, `kimi`, `adk_cloud_run`. `AgentOrchestrator._ensure_provider_registry` still registers dedicated spawn backends for `grok`/`openai`/`gemini`/`kimi` (each its own CLI-based provider, inherited from the predecessor's multi-provider work) alongside `adk_cloud_run`. On this deploy none of the four CLI providers is ever dispatched to: `seed_adk_cloud_run_routing` runs at every boot with `gcp_project_id` set and unconditionally upserts a GLOBAL routing assignment pinning every agent at `ADK_CLOUD_RUN` (`robofleet/services/llm.py`), and nothing in the seeded deploy overrides it per-role or per-agent. The predecessor's `anthropic` (Claude Code CLI, docker-spawned) path was removed outright — `_spawn_container` raises `RuntimeError` if a resolved `provider_type` has no registered backend, rather than falling back to a stripped code path.

## Honesty: what's inherited but not live on this deploy

- **MCP servers** (`robofleet/mcp/`) still exist and back the two **interactive** chat roles, Intake and Secretary — human-facing task drafting and a CEO chief-of-staff. Both spawn as long-lived local containers via `AgentOrchestrator._run_container_cmd`, a literal `docker run` subprocess, unchanged from the predecessor. Since the orchestrator's Cloud Run container has no Docker daemon (confirmed: no socket is mounted, nor could one be on Cloud Run), that spawn fails there — these two roles are not functional on the actual Cloud Run deployment described in this document. Every delivery-lifecycle role (developer/QA/documenter/PM/PR-reviewer/board) is unaffected: none of them go through `_run_container_cmd`, all of them go through `CloudRunJobsProvider`.
- **The Telegram notifications bridge, the video-render engine** (Remotion/HyperFrames compositions plus a separate `video-renderer` Node service and Dockerfile), **and the X/Twitter posting engine** are present in code, each behind its own feature flag, and each explicitly left off in `.env.gcp.example` for this deploy.
- **The Grok/Codex/Gemini-CLI/Kimi provider backends** described above remain fully implemented, including their own Dockerfiles (`docker/agent-grok.Dockerfile`, `agent-codex.Dockerfile`, `agent-gemini.Dockerfile`, `agent-kimi.Dockerfile`, plus dedicated Gemini/Grok prompter and secretary variants for the interactive roles) — `docker-compose.yaml` still builds all of them for local dev, but `cloudbuild.yaml` (the GCP image pipeline) builds only the three images this deploy uses, and they are dead-routed per the seed above regardless — reachable only if an operator manually overrides the routing table.
